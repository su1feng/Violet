# 000 定位

## 它是什么

Violet 是一个**常驻的个人 agent**：在你自己的机器上长期运行，按事件醒来、做完事、保存状态、重新睡回去。

"常驻"不是形容体验的口号，是架构描述。它意味着：

- 触发不只有你说的那句话。还有定时器、webhook、你之前的回复。
- 每次醒来都要知道自己是谁、上次做到哪、答应过什么。
- 没有任何人在旁边看着它。所以它必须事前被授权，事后能说清凭什么。

## 第一原则

**尽可能少占用人的注意力，尽可能多给价值。**

每个部分都按这条原则判断：一条消息、一次提问、一个面板元素、一个设置项，都要给出比它消耗的注意力更多的价值，否则删掉。

这条原则来自 DeepSeek 的 dsh-superagent 研究原型（MIT 许可），它的 `000-philosophy.md` 把这个想法写得比我们能写的更准确：

> 一个能为整个团队行动的 agent，也能浪费整个团队的时间。
>
> —— "An agent that can act for a whole team can also waste a whole team's attention."

个人 agent 的问题完全一样，只是规模从"团队"变成"你自己"。

## 三份材料的取舍

Violet 的设计不是凭空来的。三份材料各自给了一块，边界很清楚：

| 材料 | 给了什么 | 没给什么 | 我们怎么用 |
| --- | --- | --- | --- |
| Anthropic《Building always-on agents》 | **环路**：事件收件箱、定时器、记忆、权限、发件箱五个原语 | 只有机制，没有业务语义；"该不该做"这一层完全没有 | 照做，它是这个问题的规格说明 |
| DeepSeek `dsh-superagent` | **授权**：Source → Trigger → Thread → Eval → Mandate → Ticket → Assignment 的实体链，以及"授权不可变、策略版本化" | 它是给团队仓库做代码 agent 的；明确拒绝了定时器；没有记忆子系统 | 抄域模型，按个人场景收缩 |
| `OpenMausBot` / `rakazo` 等 | **验证**：证明同样的骨架能撑住完整产品（记忆文件布局、审批映射到各 CLI 原生模式、崩溃恢复语义） | 它们是完整商业产品，功能面不是我们的目标 | 只当证据，不对标功能 |

**三者相通的部分是已验证的共识，直接采用；分岔的部分是自己的判断，写在 [006 决策记录](006-decisions.md)。**

## 不做什么

明确列出来，因为"不做什么"比"做什么"更能定义产品。

| 不做 | 理由 |
| --- | --- |
| 多 bot 人格市场、群聊、bot 之间协作 | 一个人用，第一个 bot 跑稳之前不知道第二个该长什么样 |
| 团队、成员、权限下放、审批链 | 多用户是另一个产品 |
| 云端、账号、计费、托管 | 数据在你机器上，服务只监听本机 |
| Electron 桌面端、iOS、手机推送 | 先把环路跑对，外壳随时能加 |
| 语音、会议、图像生成 | 与"常驻决策"这个核心无关 |
| 自建浏览器控制、自建桌面控制 | 巨大子系统，个人场景不需要 |
| 自己实现 agent loop | 见下 |

## 不自己实现 agent loop

这是四份参考实现一致的决定，我们照跟：

- `dsh-superagent` 把执行交给 DeepSeek Harness，自己只写 Source / Eval / Ticket / Executor 那一圈
- `LoopForge` 直说"CodeBuddy、Codex、Claude Code 干活，LoopForge 加角色、沙箱、检查点、历史"
- `rakazo` 有独立的 `adapter-kit` 和 `adapters` 包
- `OpenMausBot` 走 ACP 协议

模型调用、工具循环、上下文压缩、重试、流式输出、权限拦截——这些东西已经有四代人在优化，我们自己做只会做到第七十分。

**Violet 的全部价值在 loop 外面那一圈：什么时候醒、该不该做、做完了告诉谁、凭什么。**
