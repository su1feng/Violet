# 006 决策记录

每一条记的是"当时为什么这么选"，不是"现状如何"。现状看代码。

## D1 · 不 fork 任何现成项目，从零新建

**背景：** 候选是 fork `deepseek-harness`、fork `dsh-superagent`，或者新建。

**决定：** 新建。

**理由：**

1. **dsh-superagent 不是 fork。** 它整个仓库只有几十个文件，靠一个 8.5KB 的 `cordis.patch.yml` 声明往 harness 里插哪些插件。DeepSeek 自己都没 fork deepseek-harness。
2. **fork 会把架构锁死在 Cordis 的依赖注入范式上。** 而我们的正确性论证全部建立在"`core` 能用内存实现跑测试"之上。Cordis 是服务容器，`core` 会天然依赖容器。
3. **要写的那部分，dsh 一个都没有。** 59 个包里，`memory`、`inbox`、`outbox`、`notify`、渠道、授权模型全部缺失——这正是 dsh-superagent 要写两千多行的原因。fork 进来 59 个包，实际用 3 个。

**代价：** 面板、桌面端、沙箱全得自己写。

**什么情况下会改主意：** 如果面板成了瓶颈，或者打算长期跟随 deepseek-harness 的插件生态。

## D2 · deepseek-harness 作为执行器接入，而非底座

**决定：** `dsh --profile acp` 起一个 ACP 服务，像 claude / codex / pi 一样接进来。

**理由：** 它的 API 和我们的执行器接口逐条对上——创建/恢复会话、选模型与思考强度、挂 MCP、提交与取消、接收语义更新。而它明确是 "automation-only" 的，本来就为程序化客户端设计。

**收益：** 白拿会话持久化、沙箱、调度实现，不继承架构约束。

## D3 · 一轮一个子进程，不做长驻会话

**理由：** 常驻 agent 的失败模式是半夜挂了要能恢复，而长驻进程把会话状态放进了内存——正是最该被恢复的东西。一轮一进程省掉一整类问题。

**代价：** 冷启动 1–2 秒；放弃 prompt cache 预热；**拿不到 `steer`**；一轮内的后台工作活不过这一轮。

**交叉证据：** `dsh-superagent` 的 worker 也受"turn 内结束"的约束（后台工作 30 分钟上限）。这说明即使有长驻会话，常驻 agent 的调度仍然要按"turn 为界"设计。

## D4 · SQLite，不是 Postgres

**理由：** 单进程单 worker，同步事务让"抢占事件"这个原语变得平凡。备份就是拷一个文件。

**代价：** 多用户或多机器时要换。`store` 是独立包，换实现不动上层。

## D5 · `outbox.reason` 是必填枚举

**理由：** 账本要能算，分类必须事先固定。自由文本三个月后没人能聚合，"该不该降频"就只能凭感觉。

**这是 Violet 的差异点所在**——两份主材料都只说"要少打扰人"，没有把注意力做成可统计的数据。

## D6 · accept mode 默认 `observe`

**理由：** 这是建立信任的唯一手段。先跑一个月看它"本来打算做什么"，再决定要不要开 `auto`。

**参考：** dsh-superagent 默认 `observe`，并写明"先看记录，再切 auto"。

## D7 · 授权不随策略变更撤销在跑的工作

**理由：** 取消会留下半成品，而"留一个半成品要求人收拾"比"让它跑完"更消耗注意力。变更以通知形式送达，由在跑的工作自己判断。

## D8 · 不自己实现 agent loop

**理由：** 四份参考实现一致这么做。Violet 的价值在 loop 外面那一圈。

## D9 · 提问结束这一轮，不挂起

**理由：** 三家 CLI 对"运行中注入输入"的支持各不相同，依赖它就绑死在一家上。"起进程 → 给 prompt → 拿结果"是最低公共下界。

## D10 · 定时器错过的触发，12 小时内合并成一次

**理由：** 不这么做，笔记本合盖一夜、第二天开机会收到七个昨天的日报，一次烧光信任。

**来源：** OpenMausBot 的 `routine-schedules.md`，它踩过这个坑。
