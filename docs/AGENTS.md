# 给 agent 的工程规则

在这份仓库里改代码之前读这篇。它比 [007 质量工程](007-quality.md) 短，因为它是**日常规则**，不是设计理由。

## 改之前

1. 读相关的 `docs/00X-*.md`。文档是设计的唯一描述，代码是它的实现。两者不一致时，先确认哪个是错的。
2. 确认这次改动属于哪个包。**包边界就是架构边界**，跨层 import 会红。
3. 如果这件事需要改文档里的表结构或能力表，**同一份 commit 里改两边**。

## 四条不可违反

| 规则 | 违反后果 |
| --- | --- |
| `packages/core` 不加任何依赖、不做 IO | `verify-deps` 红 |
| 不用 `any` / `as unknown` / `!` | oxlint + `verify-types` 红 |
| 文件不超过 400 行 | `verify-file-size` 红 |
| 文档里不用含糊词（清单见 `scripts/concrete-terms.ts`） | `verify-concrete-terms` 红 |

## 加一个门

按顺序问，**不要跳过前面的步骤直接写门**：

1. 这个错误能不能从设计上消灭？（改类型、改 API、改边界）
2. 能消灭就消灭，**不要写门**。
3. 消灭不了才写门。

写门时的四条硬要求：

- [ ] 有对应的 `scripts/verify-X.spec.ts`
- [ ] spec 覆盖三种情况：干净通过、有违规报错、**空语料报错**
- [ ] 失败信息说清"该做什么"，不是只说"不许做什么"
- [ ] 单次运行 < 2 秒

四条缺一条，宁可不建。

## 改一个门

门的放宽必须显式：

- 提高 `doc-budgets.manifest.json` 的数字 → PR 描述里写理由
- 修改 `file-size.baseline.json` 的数字 → **只能减不能加**
- 改 oxlint 规则集 → 会改变指纹，`verify-lint-config` 会红，这是故意的

## 修一个 bug

先问：**这是不是会重复出现的错误？**

- 会 → 按"加一个门"的流程，先让门在旧代码上红，再修
- 不会 → 直接修，别过度工程

PR 描述里加一行 `降级：第 N 层`（N = 1..4，见 [007](007-quality.md#一降级链在-violet-上的投影)）。这是唯一能看出"在建机制还是在堆期待"的信号。

## 写文档

- 新文档必须同时加进 `scripts/doc-budgets.manifest.json`，否则不会被检查覆盖
- 文档里的代码块如果描述真实代码，必须能被检查覆盖；只是示意就标注「示意，不参与检查」
- 写不出确切值，说明这件事还没想清楚。不要用含糊词掩盖
- 每篇只在开头说一次它依赖哪些文档，不要互相前置引用

## 提交

- 一个 PR 只做一件事。移动代码和改行为不要混在一起
- commit message 说"为什么"，不说"改了什么"（diff 已经说了）
- 不提交 `*.db`、`node_modules/`、`.env`

## 不要做

- 不要自己实现 agent loop（见 [000 定位](000-positioning.md#不自己实现-agent-loop)）
- 不要在 `core` 里读文件、读环境变量、读时钟（注入 `Clock` 端口）
- 不要为了让测试过而降级断言（`expect(...).toBeTruthy()` 改成具体值）
- 不要新增"以后可能会用"的抽象。三处重复之后再抽
